# Process

> How changes to **this repo** get made: its code, config and the tooling around them. Adapted from
> Anthropic's [AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) for a
> small team whose primary harness is Claude Code. `/sdlc:setup` wrote this; it is this repo's now,
> so change anything that doesn't fit. The skills find it through `[docs] process` in
> `.sdlc/config.toml`.

## The point of the process

A wrong boundary file reaching the people who render it: an area missing from, doubled in, or
filed under the wrong parent, or a file moved out from under a URL someone hotlinks.

The files are generated by scripts and committed by the thousand, so a fix arrives as a diff no one
can read: a municipality filed under the wrong province (Davao City in Davao del Sur) or a district
with none of its municipalities (NCR) looks like any other change to coordinates. Users find it
after they have drawn the map. Everything below exists to put a checkable claim between a change
and the people who rely on it.

**The process is a plugin.** The stage machinery lives in the `sdlc` Claude Code plugin, whose
skills are `/sdlc:setup`, `/sdlc:intent`, `/sdlc:spec`, `/sdlc:ship`, `/sdlc:close`, `/sdlc:drop`,
`/sdlc:release`, `/sdlc:publish`, `/sdlc:retro`, `/sdlc:status`, `/sdlc:health` and
`/sdlc:uninstall`. The plugin owns *mechanism*; this repo owns *policy*: this
file, the policy doc (`[docs] policy`, `CLAUDE.md`, or `AGENTS.md` when that is the only one),
which holds the invariants a design stays inside, the review passes (`.sdlc/REVIEW.md`) and
`.sdlc/config.toml`, which names the commands the skills run. The skills read all of it through
`sdlc.py config`.

## The six stages

| Stage | What it is here | Artifact |
|---|---|---|
| **1 Plan** | Capture why a change is worth making, in your own words | `intent.md` |
| **2 Design** | Requirements and design, inside the invariants in the policy doc | `spec.md` (Tier 2) |
| **3 Build** | Claude Code plan mode, then implementation | `plan.md` (Tier 2) |
| **4 Test** | The gate, and the slower check when the diff calls for it | `commands.check`, plus a change's own `checks.md` |
| **5 Ship** | A reviewed commit | the commit |
| **6 Maintain** | `/sdlc:health` runs the scans and tiers what they find | a new `intent.md` |

`.sdlc/work/inbox.md` sits *before* Stage 1: where change requests arrive, explicitly not a backlog.
Promoting a seed into committed work is what `/sdlc:intent` does. When `/sdlc:ship` closes a seed,
`sdlc.py ship` deletes the entry its `idea:` names and stages it with the rest of the change, so
`inbox.md` holds only what is open; history keeps the rest.

```
.sdlc/work/inbox.md ──/sdlc:intent──▶ intent.md ──/sdlc:spec──▶ spec.md ──plan mode──▶ plan.md
   ▲                                                                                │
   │                                                                           implement
   └──────────────  /sdlc:health  ◀────── maintain ──  /sdlc:ship ────────────┘
                 (Stage 6 tiers findings; response tier 3 writes a new intent)
```

### Seeds, and the changes they become

Every entry in `.sdlc/work/inbox.md` is a **seed**: something a change may grow from. Its tag is its
kind, which says where it came from:

| Seed | What it is | Written by |
|---|---|---|
| `[idea]` | a change someone proposes: something new, or something better | `/sdlc:idea`, `/sdlc:retro`, `/sdlc:ship` carrying a note |
| `[bug]` | something already shipped that is broken | `/sdlc:bug` |
| `[nit]` | a finding `/sdlc:ship` approved unfixed | `/sdlc:ship` |

`[building]` marks an idea a change is building. A `[seed]` tag, from before ideas had their own,
reads as `[idea]`.

A change has a **type**, which says what it does: the word a changelog or a commit prefix would
use. The kind of seed suggests the type, never fixes it:

| Type | What the change does | Usually grows from |
|---|---|---|
| `feature` | adds something a user can do or see | an idea |
| `fix` | makes something broken work as it should | a bug |
| `refactor` | changes the code's shape, not what it does | a nit, an idea |
| `perf` | makes something faster or cheaper, nothing else | an idea, a nit |
| `docs` | changes only documentation | an idea, a nit |
| `test` | adds or fixes tests alone | a nit |
| `chore` | tooling, dependencies, process: nothing a user sees | an idea, a nit |

The type is apart from the tier (how much ceremony a change owes) and from `impact:` (what a
release does to its users): a `fix` can be a `minor`, a `feature` a Tier 1. These are the words
the plugin uses; a repo whose commits name a type, as a prefix (`fix: …`) or otherwise, uses
them, and one whose commits don't leaves them out.

## Three loops

The six stages are one loop, run once per change. Two slower loops sit around it, and each one
takes in what the loop inside it produced:

```
┌──────────────────────── retro loop · /sdlc:retro ─────────────────────────┐
│  ┌──────────────── release loop · /sdlc:release, /sdlc:publish ────────┐  │
│  │   ┌─ change ─┐   ┌─ change ─┐   ┌─ change ─┐                        │  │
│  │   │ intent → │   │          │   │          │   … any number          │  │
│  │   │ … → ship │   │          │   │          │                         │  │
│  │   │ → close  │   │          │   │          │                         │  │
│  │   └──────────┘   └──────────┘   └──────────┘                         │  │
│  │   closed changes ─▶ version, tag, notes ─▶ pushed and published      │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│   history and releases ─▶ findings, milestones ─▶ direction doc, seeds     │
└───────────────────────────────────────────────────────────────────────────┘
        ▲                                                            │
        └──────── seeds become intents: the next change loops ───────┘
```

| Loop | Runs | Takes in | Leaves | Gate |
|---|---|---|---|---|
| **Change** | once per change, several in parallel | an idea, a finding, a seed | a reviewed commit on `main` (ship), its folder archived (close) | one WAIT each at intent, spec, ship, close |
| **Release** | once per batch of closed changes | the `impact:` of each change closed since the last tag | a version, a tag and its notes (release); then the push and the host's publish (publish) | one WAIT at release, one at publish: reversible and irreversible kept apart |
| **Retro** | when `status` says Retro due (2 releases, or a major one), or when the direction is unclear | the history since the last retrospective, its releases, the process and policy docs, the product doc (if any) with its evidence and what each change served, the skills, and what each change cost | the direction doc (goals, milestones, the next major release), the product doc's outcome lines, and seeds in `.sdlc/work/inbox.md` | one WAIT |

**No loop reaches past the one inside it.** A release only takes changes that have closed. A
retrospective never edits code or skills; what it finds goes back in as a seed and comes out the
other end as a change. `/sdlc:health` belongs to the change loop: it is the playbook's
Maintain detection, and what it finds becomes the next change's intent. The retrospective is the
slower question: whether the loops themselves are working, and where they should go next.

### Where the playbook fits

| The playbook | Here | How much the playbook says |
|---|---|---|
| Plan, Design, Build, Test | change loop, Stages 1–4 | its core, and prescriptive |
| Deploy: review, a person approves | Stage 5, Ship | covered: review in passes, Important vs. nit, one approval |
| Deploy: "the agent prepares the release and the release manager authorizes it" | release loop | **the gate only.** Versioning, the release boundary and release notes are absent ("draft the changelog" is the one mention). Here: `impact:` at ship, the bump rule, a tag as the boundary |
| Maintain: deterministic detection, tiered response | `/sdlc:health`, inside the change loop | covered |
| Maintain: measure the loop | retro loop, process pass | **thin.** Indicators are named for each play; nothing says when they're read or which decision they feed |
| Maintain: "once a month the tech lead tunes the setup" | retro loop, process and cost passes | **thin.** Tuning review findings, not reviewing the process as a whole. Cost is spend limits only; "detection stays deterministic" is never applied to the process's own steps |
| *absent* | retro loop, product and direction passes | **absent.** No roadmap, milestones, next major release, product outcomes or backlog replacement: planning beyond one intent is outside the playbook |
| "the process becomes a loop" | three nested loops | **one loop.** Loops at different cadences aren't described |

## Tiers: the overhead control

**This is the load-bearing rule.** A process that demands three documents for a one-line fix gets
abandoned in a fortnight. Most changes are Tier 1.

| Tier | What it covers | Artifacts |
|---|---|---|
| **0 — trivial** | a typo, a comment, a one-line fix nothing depends on | **none.** No folder. Commit directly. |
| **1 — small** | a field added, a test added, a doc section, a flag | `intent.md` only; its **Approach** section stands in for spec and plan |
| **2 — substantial** | anything that changes what something already relied on means, anything an invariant in the policy doc comes near, anything with a live consumer | `intent.md` + `spec.md` + `plan.md` |

When it's borderline, **pick the lower tier**. A Tier 1 that grows can be promoted by editing
`tier:` and running `/sdlc:spec`. A Tier 2 that didn't need to be one just doesn't get written.

**Always Tier 2, whatever the size of the diff:**

- **Anything with a live consumer.** Something nobody uses yet is cheap to get wrong; something
  people already rely on is not, and the tier should reflect who finds out.
- **Re-running a generation script over a level.** One command, but it rewrites every file of that
  level for everyone using that vintage, and the diff is too large to review by eye. The spec names the
  PSGC codes that should change, and verification proves only those did.
- **A new vintage directory** (`<year>/`). It is where every new user starts, and its layout
  becomes public API the day it is pushed.

## The artifacts

One folder per change, `.sdlc/work/NNN-slug/`, committed on the change's own branch in its own
worktree. The artifacts are reviewed in the same diff as the code they describe, and everything
about a change reads top to bottom in one place. When the change closes, its folder leaves `main`
in a commit of its own; history keeps it (*Closing and the archive*, below).

Frontmatter lives on `intent.md` only, so there is one place a stage can be wrong:

```yaml
id: 003
slug: reopen-drafts
tier: 2
impact:            # settled by /sdlc:ship: major | minor | patch | none
stage: plan        # plan | spike | design | build | test | ship | shipped | dropped
created: 2026-10-17
updated: 2026-10-17
idea:              # optional backlink: the id of a .sdlc/work/inbox.md entry (a title, before ids)
depends_on:        # optional: the open changes this one waits on, by id, e.g. [003]
dropped_at:        # stamped by /sdlc:drop: the stage a dropped change reached
```

**`stage: spike`: trying something to throw away.** Set it from any stage to explore (a library, a
shape, whether something is possible at all), and set the stage you left when you're done. A spike
owes no artifact, and `/sdlc:close` reports its cost apart (`Sdlc-Spike`), never as rework: a
change that chose to learn first shouldn't look worse than one that guessed.

**`intent.md`: why.** Problem · Outcome · Affected · Constraints · Open questions (+ **Approach**
for Tier 1). Write the problem as a problem, not a solution in disguise: *"the report page takes
forty seconds to load"*, not *"add a cache"*. An intent with unresolved open questions is
finished; resolving them is Stage 2's job.

**`spec.md`: what.** Requirements · Design · Contracts touched · Alternatives rejected ·
Verification. The requirements are the point: each independently checkable, because they become
the review's checklist. *"R4. Saving a draft twice keeps one draft, and a test fails if a second
appears"*, not *"drafts should work"*.

**`plan.md`: how.** Files to change · Work order · Tests · Rollback. **Don't hand-write this.** Its
value is that Claude read the code before writing it, which is what plan mode does. Approve the
plan, then save it here. **Rollback** says what `git revert` doesn't undo, if anything: data
written, a migration run, something published, and the command that reverses each.

**`notes.md`: what happened.** Optional and free-form, with one rule: **anything left undone is an
unticked `- [ ]` line**, not an empty table cell or a "still to check" heading, which the tools
can't see. `/sdlc:status` counts them, and `/sdlc:ship` gives each a disposition: carried to a new
`.sdlc/work/inbox.md` seed, or dropped with a reason. `sdlc.py ship` refuses while one is unticked.

## Where a change is worked: one worktree per change

**One change, one number, one folder, one worktree, one branch, all named `NNN-slug`.**
`/sdlc:intent` settles the number first, makes the worktree at `.claude/worktrees/NNN-slug` and
its branch off `main`, makes the folder inside it, and moves the session into it. Everything for
that change happens there, artifacts included, up to `/sdlc:ship`; only `/sdlc:close` and `/sdlc:drop` leave it.

**The number** is the change's GitHub issue when `archive.target` is `github`: `/sdlc:intent`
opens the issue, and GitHub never hands a number out twice. Otherwise `.sdlc/last-id` numbers
changes: `/sdlc:intent` writes it in the change's worktree and the change's commit carries it to
`main`, which is only safe on one machine. `sdlc.py config` says which is in use.

**The main checkout stays on `main`.** Changes are merged there: `/sdlc:close` fast-forwards `main`
in the main checkout, and refuses while it is on another branch or has uncommitted changes. Start
new changes from it too; `sdlc.py status` there lists the open changes in every worktree,
marking a branch `main` has moved past. `/sdlc:ship` brings such a branch up to date before the
gate runs, so the tests and the review see what will land, and stops, touching nothing, when
that would conflict.

A fresh worktree has no source shapefiles: they are gitignored, and the generation scripts fetch
them on their first run (`scripts/fetch-shapefiles.sh`, from a local
`philippines-psgc-shapefiles` checkout or the
[faeldon/philippines-psgc-shapefiles](https://github.com/faeldon/philippines-psgc-shapefiles)
release, about 700 MB per quarter). A change that regenerates needs `gdal` and `mapshaper`
installed. `commands.worktree_setup` is unset because most changes don't regenerate.

## Running the stages

### Stage 1 — Plan → `/sdlc:intent`

Interviews you, assigns a tier, drafts `intent.md`, gates, then opens the change (its GitHub issue
first, when that's how changes are numbered) and **stops**. If the change came from a
`.sdlc/work/inbox.md` seed, it sets the `idea:` backlink and marks the idea `[building]`.

A data-error report becomes an intent that names the PSGC codes involved and the parent each
belongs under in the PSA's PSGC release. "Fix Davao" is not an intent; one that says which area
(its code), which file it is in now, and which file it belongs in is.

### Stage 2 — Design → `/sdlc:spec`

Tier 2 only. Reads `intent.md` and the invariants in the policy doc, resolves the intent's open
questions (striking them `~~like this~~` rather than deleting them), drafts `spec.md`, gates, and
advances `stage: design`. **The invariants are this repo's policy.** A spec that can't stay inside
them is telling you something: change the invariant on purpose, with its own reasoning, or change
the design.

### Stage 3 — Build → plan mode

No skill; plan mode already *is* this stage, and a skill would only compete with it. Start a
session in plan mode, point it at `spec.md` (or the intent's Approach), interrogate the plan,
approve it, save it as `plan.md`, advance `stage: build`, and implement. **Nothing is implemented
without an accepted plan.** A Tier 2 change owes `plan.md` from `stage: build` on, and
`sdlc.py check` says so; for Tier 1 it's worth saving when the plan touches more than a couple of
files. When the build departs from the plan, update `plan.md` in the same commit: a plan that no
longer says what was built misleads the review that reads it.

**The policy doc is the standing context**: under a page, checked into git. When Claude makes the same
mistake twice, the correction goes into it; `/sdlc:ship`'s context pass is where that is weighed.
A skill is a control, but an advisory one: a rule that must always hold needs a hook or a test
behind it, not only a sentence in a skill.

### Stage 4 — Test

Advance `stage: test` and run what proves the change. **Two kinds of check, split on purpose:**

- **The gate** (`commands.check`): fast, offline and free of side effects, and what `/sdlc:ship`
  runs every time. Offline on purpose: a gate that needs the network gets skipped, and a skipped
  gate still reports green from memory.
- **The slower check** (`commands.build`): whatever needs real services, real data or real time.
  `/sdlc:ship` runs it when a changed path matches `commands.build_when`, and on every change
  when `build_when` is unset.

The gate (`commands.check`) parses every JSON file under `latest/` with `jq`, and fails if
anything not ignored, tracked or untracked, sits under a build directory (`<quarter>/`), `dist/`,
`scripts/20*`, or any `hires/`: only `latest/`'s medres and lowres are committed. It also fails
if any commit on `HEAD` carries a `Co-Authored-By: Claude` trailer (017). There is no slower check: regenerating needs the source
shapefiles, `gdal` and `mapshaper`, and the scripts `rm -rf` their output first. So a change that
regenerates proves its codes in `checks.md`: for example, a `jq` check that a municipality's
code appears in its parent's file and in no other file at that level. Always give Claude a way
to verify its own work: the policy doc says what healthy output from each looks like.

**A bug fix starts with a failing test.** Commit the test that fails because of the bug first,
then fix the code without editing the test.

**Ask of each test how it could ever fail**, because that decides how long it lives:

- **Regression:** a later change breaks it by accident. It goes in the suite and stays.
- **Compatibility:** it fails when a shim stops working. It lives exactly as long as the shim,
  which names the version that removes it, in `release.deprecations` when the repo keeps one,
  else in a comment; the test goes with the shim.
- **Acceptance:** only a deliberate revert breaks it: a file moved, a key renamed, a section
  added. Write it as a `## ` section of the change's `checks.md`, one `sh` block that exits 0
  while the outcome holds; `/sdlc:ship` reruns it before it commits. One that can't run, such as
  looking at a rendered page, is recorded in `notes.md`: what was done and what it showed. Either
  way it reaches history with the folder and stays out of the suite, where every later run would
  pay for a check nothing can break by accident.

A test run that collected nothing is a failure, not a pass: it means discovery broke, and a green
gate that ran zero tests is the quietest way for a broken change to reach `main`.

### Stage 5 — Ship → `/sdlc:ship`

Shipping is a reviewed commit: run the gate → the slower check if the diff calls for it → review
the diff → give each undone `- [ ]` a disposition → settle the release `impact:` → **one approval**
→ the approved context-doc edits → `sdlc.py ship` stamps the intent `stage: shipped` → one commit
naming the change (`Refs #NNN` when its number is a GitHub issue), carrying the code, the context
docs and the change's folder. `/sdlc:ship` never pushes and never deploys.

**The review** has four passes. The first three are `.sdlc/REVIEW.md`'s: **correctness** against
the numbered requirements · **contract** against the invariants in the policy doc · **cost and
simplification**. The fourth is the plugin's: **context**, whether the policy doc and the other docs
that give a session its context still tell the truth after the diff. Findings are Important or Nit;
nits cap at 5, and more than 5 means the change is too big.

Pushing `master` is publishing: users hotlink `raw.githubusercontent.com/.../master/...`, so a file
is live the moment the push lands. There are no `release.version_files`, so `/sdlc:release` bumps
nothing and pushing `master` is done by hand after `/sdlc:close`. Ship stops before it.

#### Nits: small technical debt

A Nit approved unfixed isn't lost in the findings count: ship records it in `.sdlc/work/inbox.md` as a
`[nit]` entry, with `Theme:`, `Paths:`, `Cost:`, `Value:` and `Raised by: NNN-slug (pass)` lines,
and a later ship retires it once a diff fixes it or makes it moot. Each is weighed the same way:
- **cost:** `S`, one sitting and a few lines · `M`, a test or several files · `L`, a design call.
  An `L` is a `.sdlc/work/inbox.md` idea, not a nit.
- **value:** `med`, a user or host could hit it on an edge case · `low`, only a reader of the code
  notices. One users would hit in normal use, or that loses work, is never a nit: it is Important.
- **theme:** `docs`, `refactor`, `robustness`, `tests` or `style`, or one of this repo's own, so
  like is paid down with like.

An `S` with `med` value is worth fixing before the commit that found it. `/sdlc:intent` (Tier 1)
and `/sdlc:spec` (Tier 2) offer the open ones on the paths a change touches, so changes pay debt
down as they pass. A theme with 5 or more open, or any nit older than 60 days, is what
`/sdlc:retro` proposes one change to pay down. Release and publish never look at them: the release
cycle is for shipping.

#### Bugs: what's already broken

A bug is something that shipped and is broken, with a way to see it: a `[bug]` entry in
`.sdlc/work/inbox.md`, filed by `/sdlc:bug` with `Severity:` and `Paths:` lines, and an
`Introduced by: NNN-slug` line once someone confirms which change let it through. A request for
something nobody has built is an idea, and a finding in a diff under review is a nit or Important.
Each is weighed the same way:
- **severity:** `high`, it loses work, gives a wrong number or stops a stage · `med`, its output
  is wrong and there is a way round it · `low`, a message or a rough edge.

`/sdlc:status` puts open bugs first, most severe first. `/sdlc:intent <id>` opens the change that
fixes one, its intent naming it on a `fixes:` line; `/sdlc:ship` removes the entry with the fix,
and `/sdlc:close` records it on the `Close` commit as an `Sdlc-Fixes:` trailer, so history says
which change fixed what. One that needs no fix is retired by `/sdlc:bug`, with its reason.
`/sdlc:retro` counts them: reported, fixed and retired in its window, days from report to fix,
and escapes per introducing change against its tier.

### Closing and the archive → `/sdlc:close`

After ship, behind one approval, one command: bring the session back to the main checkout,
fast-forward `main` (`--ff-only`), mirror the change to its tracker (its GitHub issue, or the command in `archive.command`) and read the copy back,
remove the folder from `main` in a `Close NNN-slug` commit, remove the worktree (never `--force`)
and delete the branch (`-d`, never `-D`). With nowhere to mirror to (`archive.target = "none"`),
the folder still goes: the change's own commit holds it.

### Dropping a change → `/sdlc:drop`

A change that won't ship is dropped, not deleted, at any stage. `/sdlc:drop`, from its worktree,
asks why and writes the answer as a `## Dropped` section of its intent. Behind one approval,
`sdlc.py drop` stamps `stage: dropped` and `dropped_at:` (the stage it reached) and commits the
folder on its branch, and close finishes it: the issue is closed as not planned, and `main` gets
a `Drop NNN-slug` commit, a merge that keeps `main`'s files (`git merge -s ours`), so the branch's
commits stay reachable and `-d` can delete the branch. Nothing of the change lands, but its
number stays spent, and the retrospective counts what didn't ship and how far it got. A drop
that stops partway is finished with `/sdlc:close`.

**Each artifact has one source of truth**: its folder on the change's branch while it is open, and
that commit, in `main`'s history, once it closes. The tracker mirrors it for reading.

**The issue follows the change.** A tracker is optional (`archive.target`; `none` runs none), and
only Tier 1 and 2 changes reach one. With GitHub, the change's issue carries `tier:`, `stage:` and
`impact:` labels, is assigned to whoever opened it, and is blocked by the issue of each change in
`depends_on:`. `sdlc.py sync` rewrites it from the artifacts after the approvals of
`/sdlc:intent`, `/sdlc:spec` and `/sdlc:ship`, so it reads as the change stands; stages set by
hand (build, test) show at the next sync. Edit the artifacts, never the issue: sync overwrites it.

A repo with its own project management adds a project doc (`docs.project`, `.sdlc/PROJECT.md`):
its frontmatter turns on the issue's milestone, project and assignees and says where each one's
values come from, and its prose says how to choose. `/sdlc:intent` offers only what
`sdlc.py lookup` lists, records the answers in the intent's frontmatter, and sync mirrors them
exactly. Without the doc, none of this runs.

### The release loop → `/sdlc:release`, then `/sdlc:publish`

After a batch of closed changes, from the main checkout. **The agent prepares the release and a
person authorizes it**, in two steps with an approval each:

1. **`/sdlc:release`** lists every change landed since the last release, read from history: each
   `Close NNN-slug` commit names one, and the change's own commit before it holds the `impact:`
   ship settled. It proposes the version they add up to, and after one approval sets it in each
   file `release.version_files` names, adds the notes to `release.changelog` if one is set, runs
   `release.after_bump` if one is set (a lock file regenerated from the new version, say),
   then `release.prepare` if one is set (a build of what publish will upload, into untracked or
   ignored paths only), commits `Release X.Y.Z` with what all of that changed, and tags it (`release.tag`,
   `v{version}` by default). All local: until it is published,
   `git tag -d <tag> && git reset --keep HEAD~1` takes it back.
2. **`/sdlc:publish`** pushes `main` and the tag to `release.remote` (never forced: a remote that
   has moved is refused), then runs `release.publish`, the repo's own delivery, if it has one: an
   upload, a GitHub release, a deploy. It is the one step that sends anything anywhere, and it
   can't be taken back: a published release that turns out wrong is followed by a new patch
   release, not withdrawn.

The boundary is the tag for the version the files hold now, so a release is always everything
since the version this repo is on. Changes still open are listed and left out. With no
`release.version_files`, nothing is bumped or pushed: `sdlc.py unreleased` and `/sdlc:status` still
list what has landed, and say what to set.

**Which part to bump.** A change records at ship, as `impact:`, what it did **as seen by someone
holding the previous release**:

| `impact:` | The person holding the previous release… |
|---|---|
| `major` | has to change what they do: something renamed, removed or moved |
| `minor` | can do something new |
| `patch` | does the same things, working or described better |
| `none` | receives nothing different: tests, tooling, anything outside what is released |

**It isn't the tier.** Tier measures risk and how much ceremony a change owes; impact measures what
its users notice. `/sdlc:ship` proposes it from the diff, and `sdlc.py ship` refuses a change
without one. A release takes the highest impact among the changes since the last one, `none`
counting for nothing, and below 1.0, `major` is released as `minor`, since 1.0.0 is its own
decision, made on purpose with `/sdlc:release 1.0.0`.

### Stage 6 — Maintain → `/sdlc:health`

Deterministic detection before a model is asked anything: `commands.scan` runs the repo's scans,
and `sdlc.py check` finds intent frontmatter that won't parse, artifacts a change's tier and stage
owe but lack or never filled in, ideas marked `[building]` with nothing behind them, a `.sdlc/work/` git ignores, and a change counter that doesn't hold a number. `/sdlc:status` shows each open change's age.

No scans yet: `commands.scan` is unset. The obvious first one checks the hierarchy the bugs
broke: every feature in a child file carries its parent's code (`adm1_psgc`, `adm2_psgc`, …), and
that code should be the one in the file's name.

Findings go somewhere by **response tier**, a different scale from the change tiers above:

1. **Report**: a one-off, already understood. Note it, and why it needs nothing more: a finding
   dismissed without a reason is one nobody can check later.
2. **Fix inline**: mechanical and local. A Tier 0 or Tier 1 change, now.
3. **Write an intent**: structural, recurring, or it needs a decision. `/sdlc:intent`, and it
   re-enters Stage 1. This is the loop closing.

**Every near-miss becomes a test, in the same change that writes it down.** Prose describing a
mistake leaves the mistake available.

### The retro loop → `/sdlc:retro`

From the main checkout, when `status` says Retro due or the direction is unclear. `sdlc.py retro`
counts everything since the last `Retrospective YYYY-MM-DD` commit: the changes closed and their
tiers, impacts, sizes and problems, rework, open changes and seeds, releases, and how large each
skill is. The skill makes four passes over that and the docs: **cost** (prose doing what a script could),
**architecture**, **process** (the signals below) and **direction** (goals, milestones, the next
major release). Every finding becomes a seed, an intent title, or is dropped with its reason. After
one approval it rewrites the direction doc (`docs.direction`) and appends the seeds, and
`sdlc.py retro-commit` commits those two files and nothing else. That commit is the next
retrospective's boundary.

**It closes its own loop.** Goals (`- G1. …`) and milestones (`### M1. …`, with a `Groups:` line
naming the changes and seeds they gather) carry ids from one retrospective to the next. Each run
first scores every one the last doc left open: done, dropped (with a reason), revised to a new id
(with a reason), or carried with what's left. A closed one is struck through with its status and
stays one more retrospective. `sdlc.py retro` shows what each milestone's seeds and changes became
(a seed shipped by the change whose `idea:` names it, or vanished with none), and `retro-commit`
refuses a doc that drops an open id instead of closing it.

**When one is due.** `sdlc.py status` shows **Retro due** after `retro.after_releases` releases
since the last retrospective (2 by default; 0 turns the count off), or after any major release,
and `/sdlc:release` says so in its report. That is a nudge: the plugin never runs a retrospective
on its own. A host that wants a schedule can run its own check, a scheduled agent reading
`sdlc.py status` for instance.

## Confirm before write

Every skill that writes something real drafts the exact content, shows it, asks a literal yes/no
question, **waits**, and only then writes. Approval is **per-invocation, never standing**. Each one
has exactly one step headed **WAIT**: one rather than zero because approval is never standing, one
rather than several because a skill with two gates has an unclear boundary and the second gets
skipped.

## Signals worth watching

No dashboard for these, deliberately; they are things to notice, not things to stare at.
`/sdlc:retro` computes the ones history records, on demand, when someone asks for a
retrospective, and says which it can't.

- **Age of open intents.** `/sdlc:status` prints it. An intent at `stage: plan` for a month is a
  decision nobody has made.
- **Rework.** Changes that ship and need a follow-up fix within a week. A cluster means Stage 2 is
  being skipped. A file more than a third of the window's changes touch is left out, once there are
  six: sharing it says nothing, and the retrospective lists it apart as one most changes touch.
- **Findings caught at ship vs. found later by someone else.** The ratio is what the review buys.
- **Tier drift.** If everything is becoming Tier 2, the tier rule has stopped controlling overhead
  and needs re-drawing.
- **Where a change's time and tokens go.** `/sdlc:close` records them on each `Close` commit
  from this repo's session transcripts (numbers only; `metrics.transcripts` turns it off): per
  stage, the clocks (elapsed, agent, the person's response, away and blocked), the stops that
  waited on the person, and tokens. Time that piles up in response and away is the person's
  queue. Each change's stops are measured against its own gates plus `metrics.stop_allowance`, and
  those above that are the loop circling.
- **First time through, and rework within a change.** Close records, beside the cost, whether
  each stage went through first time (`Sdlc-Happy`) and the trial and error inside it
  (`Sdlc-Rework`); a spike's is in neither. A rising first-time rate is the loop getting better
  at the happy path. The plugin's `docs/REFERENCE.md` (*Metrics*) has every field.

## A first pass, in order

1. `/sdlc:status`: see what's open and what it recommends next.
2. `/sdlc:intent` on the next thing you want to change. Let it pick Tier 1.
3. Plan mode to build it. Save the plan if it's more than a couple of files.
4. `/sdlc:ship`. Read the review findings properly: that's the whole return on the process.
5. `/sdlc:close` once it's committed.
6. After a few of those, `/sdlc:release`, then `/sdlc:publish` when it's time users had them.

A Tier 1 intent is about fifteen lines.
